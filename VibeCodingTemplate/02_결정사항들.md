## 보완질문

### Q1. 사용자는 어디에서 어떤 단위로 동기화와 퀴즈 생성을 실행하나요?

- 질문: `동기화 버튼`은 노션, GitHub Actions, 별도 앱 중 어디에 두며, 한 번 실행할 때 대상 session을 사용자가 선택하나요? 동기화 직후 퀴즈도 자동 생성할지, 두 작업을 따로 실행할지도 정해야 합니다.
- 권장 답변과 짧은 이유: GitHub Actions의 수동 실행 화면에서 session 번호를 입력받고, `노션 동기화`와 `퀴즈 생성`을 각각 실행합니다. 별도 서버나 UI 없이 구현할 수 있고 실패한 단계만 다시 실행하기 쉽습니다.
- 답이 없을 때 적용 가능한 안전한 기본값: GitHub Actions 수동 실행을 사용하며, session 번호를 필수 입력받고 두 작업은 분리합니다.

### Q2. 어떤 노션 글을 어느 session으로 가져오며, 글에서 무엇을 저장하나요?

- 질문: 대상 노션 DB의 필수 속성(예: 제목, session, 게시 상태)과 수집할 본문 범위가 무엇인가요? 날짜로 session을 자동 판정할지, 노션의 session 속성으로 지정할지도 정해야 합니다.
- 권장 답변과 짧은 이유: 노션 DB에 `제목`, `Session`, `상태` 속성을 두고 `상태=게시`이면서 선택한 `Session`과 일치하는 페이지의 제목과 텍스트 본문을 가져옵니다. 명시적 session 지정이 날짜 경계의 모호함을 없애고 재실행 결과도 예측 가능하게 합니다.
- 답이 없을 때 적용 가능한 안전한 기본값: 속성명은 환경설정으로 바꿀 수 있게 하고 기본값을 `Name`, `Session`, `Status`로 둡니다. `Status=Published`인 페이지만 대상으로 하며, 텍스트 블록만 동기화하고 이미지·첨부파일은 원본 노션 링크만 남깁니다.

### Q3. 같은 노션 글을 다시 동기화하거나 노션에서 삭제했을 때 GitHub 파일을 어떻게 처리하나요?

- 질문: 재동기화 시 기존 Markdown을 갱신할지 중복 파일을 만들지, 노션에서 삭제·비공개 처리된 글을 GitHub에서도 삭제할지, 사용자가 GitHub에서 직접 수정한 파일과 충돌하면 어떻게 할지 정해야 합니다.
- 권장 답변과 짧은 이유: 노션 페이지 ID를 파일 메타데이터에 저장해 같은 글은 같은 파일로 갱신하고, 노션에서 사라진 글은 자동 삭제하지 않습니다. 동기화 파일의 직접 수정이 감지되면 덮어쓰지 않고 실패로 알립니다. 중복과 예기치 않은 데이터 손실을 함께 막을 수 있습니다.
- 답이 없을 때 적용 가능한 안전한 기본값: 재실행은 멱등적으로 갱신하고 자동 삭제는 하지 않으며, 충돌 파일은 보존한 채 해당 글의 동기화만 실패 처리합니다.

### Q4. 생성된 퀴즈와 정답을 어떤 파일 형태로 제공하나요?

- 질문: 각 session 안의 출력 파일명, 정답·해설 공개 방식, 출제할 수 있는 근거가 부족할 때 20문제를 반드시 채울지 여부를 정해야 합니다.
- 권장 답변과 짧은 이유: `quiz.md`에는 4지선다 문제 약 20개를, `quiz_answers.md`에는 정답·짧은 해설·근거 글 링크를 저장합니다. 근거가 부족하면 내용을 지어내지 않고 문제 수를 줄입니다. 대면 진행 중 정답 노출을 막고 사실 검증도 가능합니다.
- 답이 없을 때 적용 가능한 안전한 기본값: 두 파일을 분리하고, 기존 퀴즈 파일은 새 생성이 모두 성공한 뒤 교체합니다. 최대 20문제로 생성하되 근거가 부족하면 더 적게 만들고 그 사실을 실행 결과에 표시합니다.

### Q5. 퀴즈 생성에 사용할 AI 서비스와 인증정보를 어떻게 제공하나요?

- 질문: 사용할 AI 제공자와 API를 정하고, 유료 API 호출 및 GitHub 저장소의 암호화된 Secret 사용이 가능한지 확인이 필요합니다.
- 권장 답변과 짧은 이유: OpenAI API를 사용하고 키는 GitHub Actions Secret `OPENAI_API_KEY`로 제공합니다. 모델명은 환경변수로 바꿀 수 있게 해 특정 모델 교체가 구현을 막지 않게 합니다.
- 답이 없을 때 적용 가능한 안전한 기본값: OpenAI 호환 인터페이스와 환경변수 기반 설정으로 구현하되, 실제 API 키가 없으면 외부 호출·커밋 없이 입력 검증까지만 수행하는 dry-run으로 종료합니다.

### Q6. 일부 글의 읽기, AI 생성, GitHub 저장 중 하나라도 실패하면 무엇을 남기고 어떻게 복구하나요?

- 질문: 성공한 일부 파일만 커밋해도 되는지, 전체 작업을 실패시켜야 하는지와 재시도·오류 알림 방식을 정해야 합니다.
- 권장 답변과 짧은 이유: 실행 단위 전체를 원자적으로 처리해 하나라도 실패하면 커밋하지 않고, 어떤 글과 단계가 실패했는지 Actions 로그와 실행 요약에 남깁니다. 재실행해도 중복이 생기지 않게 합니다.
- 답이 없을 때 적용 가능한 안전한 기본값: 커밋 전 임시 결과를 모두 검증하고 실패 시 기존 저장소 상태를 유지합니다. 자동 재시도는 일시적 API 오류에만 최대 2회 적용합니다.

### Q7. 외부 연동을 포함한 MVP 완료 검증에 사용할 테스트 대상이 있나요?

- 질문: 테스트용 노션 DB·GitHub 저장소(또는 테스트 branch)와 실제 연동 검증에 사용할 권한을 제공할 수 있나요? 또한 최종 완료를 실제 커밋까지로 볼지, 모의 테스트 통과까지로 볼지 정해야 합니다.
- 권장 답변과 짧은 이유: 테스트용 노션 DB와 별도 GitHub branch에서 신규 글, 수정 글, 중복 실행, 빈 session, API 실패를 검증하고 실제 Markdown 및 퀴즈 커밋 성공까지를 완료 기준으로 삼습니다. 외부 연동의 핵심 동작을 실제 환경에서 확인할 수 있습니다.
- 답이 없을 때 적용 가능한 안전한 기본값: 자동 단위·통합 테스트에서는 노션·AI·GitHub API를 모의 처리하고, 실제 자격증명이 제공되지 않은 외부 연동 검증은 미완료 항목으로 명시합니다.
